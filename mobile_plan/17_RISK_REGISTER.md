# 17 — Risk Register

| # | Risk | Likelihood | Impact | Mitigation | Owner |
|---|---|---|---|---|---|
| R1 | Floor/dispatch staff resist adopting the app, keep using paper/verbal handoffs | Medium | High — the whole ROI case depends on real adoption | Phase 5.4's supervised pilot + in-person training; design for minimal typing/friction ([13_DESIGN_SYSTEM_UI_GUIDELINES.md](13_DESIGN_SYSTEM_UI_GUIDELINES.md)); involve a floor supervisor as a design reviewer before, not just after, build | Production Manager (pilot sponsor) |
| R2 | Offline sync bugs cause a production/delivery event to silently fail to record | Low probability, but High impact if it happens (data integrity, trust in the app) | High | Compound-action atomicity + idempotency design in [10_OFFLINE_SYNC_STRATEGY.md](10_OFFLINE_SYNC_STRATEGY.md); explicit failed-state surfacing rather than silent retry-forever; UAT data-integrity check step ([14_TESTING_QA_STRATEGY.md](14_TESTING_QA_STRATEGY.md)) | RN lead developer |
| R3 | Partner Portal guard isolation has a gap, exposing one customer's data to another or to a portal user reaching staff data | Low | Critical (trust/legal exposure) | Isolated Sanctum guard architecture (not app-level filtering) + mandatory automated isolation tests before Phase 6 is marked done ([09_BACKEND_CHANGES_REQUIRED.md](09_BACKEND_CHANGES_REQUIRED.md) §3, [12_SECURITY_COMPLIANCE.md](12_SECURITY_COMPLIANCE.md)) | Backend developer |
| R4 | Backend endpoint reality diverges from the design docs (already confirmed true for photo uploads) causes app rework mid-phase | Medium (already observed once) | Medium | [08_API_INTEGRATION_MAP.md](08_API_INTEGRATION_MAP.md)'s "verify against live routes, not docs" discipline; each phase's first week includes a Postman/Insomnia pass against the real staging API before UI work starts | RN lead developer |
| R5 | Device fragmentation (old/low-end Android used on the floor) causes performance issues not caught in dev | Medium | Medium | Mandatory P0 low-end Android testing per [14_TESTING_QA_STRATEGY.md](14_TESTING_QA_STRATEGY.md) device matrix, not just simulator testing | QA / RN lead developer |
| R6 | Push notification delivery is unreliable on Android due to OEM battery-optimization killing background processes (a known ecosystem-wide Android issue, not specific to this app) | Medium | Medium — degrades but doesn't break the app, since push is a convenience layer on top of in-app data that's still correct on refresh | Document the OEM battery-optimization opt-out instruction for pilot users; treat push as best-effort, never the sole path to critical information (in-app inbox + dashboard always reflect the same data) | RN lead developer |
| R7 | The "invite-flow decision" (Phase 6.1) stalls, blocking the entire Partner Portal milestone indefinitely | Medium | Medium (delays M2, doesn't affect Staff App) | Explicit open-decision tracking in [README.md](README.md); recommend a default (OTP, per [07_PARTNER_PORTAL_MODULE.md](07_PARTNER_PORTAL_MODULE.md)) so there's a concrete proposal to react to rather than an open-ended question | Business sponsor (Kamlesh) |
| R8 | Scope creep — a role asks for BOQ editing, dense reports, or other desktop-caliber features on mobile mid-project | Medium | Medium — threatens both timeline and mobile UX quality | Non-goals are explicit and documented ([00_EXECUTIVE_SUMMARY.md](00_EXECUTIVE_SUMMARY.md)); new requests go through a lightweight "does this belong on mobile" gate referencing that doc, not silently absorbed into a phase | Business sponsor |
| R9 | Single RN developer is a bus-factor risk for a ~30-week solo project | Low-Medium | High if it materializes | Code review discipline even with one primary developer (self-review + periodic backend-developer read-through), clear documentation (this folder), avoid tribal-knowledge-only decisions | Business sponsor / whoever staffs the project |
| R10 | App store review delays (if Partner Portal goes public distribution) push back the GA date unpredictably | Low (mitigated by recommendation to stay internal-distribution initially) | Low-Medium | Recommendation in [15_DEVOPS_RELEASE_MANAGEMENT.md](15_DEVOPS_RELEASE_MANAGEMENT.md) to defer public listing until GA scale is confirmed necessary | Business sponsor |
| R11 | Firebase/FCM dependency introduces an external service outage risk for push | Low | Low (push is best-effort per R6's framing) | No special mitigation beyond what R6 already covers — accepted risk | — |
| R12 | Stripe/Razorpay pay-now integration (optional Phase 7.5) introduces PCI/payment-compliance scope if handled incorrectly | Low (existing integration is already server-side hosted-checkout, not raw card handling) | Medium if scope is misjudged | Reuse the existing `checkout-session`/hosted-payment-page pattern already in the backend rather than building any custom card-handling UI — confirm this is still hosted-checkout style before Phase 7.5 starts | Backend developer |

## Review cadence

This register is reviewed at each phase-gate sign-off in [01_PHASE_ROADMAP.md](01_PHASE_ROADMAP.md) (0.1, 5.4, 6.1, 8.1) — risks are updated, closed, or escalated at those checkpoints rather than left static from initial planning.
